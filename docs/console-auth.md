# Console authentication (Google OAuth)

The Zonatic Developer Console authenticates with **Google only**. There is no
email/password sign-up, no password reset, and no email verification in V1.

## How it works

```
Landing page → Get Started → Console /login
  → Continue with Google
  → Google consent
  → Supabase Auth issues an access token
  → /dashboard, with a workspace provisioned on first sign-in
```

Identity is owned by Google and validated by Supabase Auth. `console-api`
never handles a Google `id_token` and never holds a Google client secret; it
only asks Supabase whether the bearer token it was given is valid.

| Piece | Responsibility |
| --- | --- |
| `apps/console` | Starts the Google sign-in, holds the session, renders the console |
| Supabase Auth | Google OAuth, token issuing, refresh |
| `apps/console-api` | Verifies the token, provisions the user + workspace, serves tenant data |
| `supabase/migrations/20260101000007_console_auth.sql` | `users`, `tenant_members`, `tenant_usage` |

The public API (`apps/api/`) is **not** affected. It continues to authenticate
`/v1/*` with `Authorization: Bearer <api key>` against `api_keys`, unchanged.

## First sign-in vs. returning user

On the first authenticated request, `console-api`:

1. creates the `users` row from the Google identity,
2. creates a default `tenants` row named after the Google profile
   (falls back to the e-mail local part, then `Zonatic Workspace`),
3. adds the user to that tenant as `owner`,
4. creates the `tenant_usage` row.

There is no onboarding form. A returning user already has a `tenant_members`
row, so the request reuses the existing workspace and lands on the dashboard.

A per-user advisory lock (`pg_advisory_xact_lock`) serialises provisioning, so
two concurrent first-time requests cannot create two workspaces for one person.

## Required environment variables

### `console-api` (server)

| Variable | Required | Notes |
| --- | --- | --- |
| `DATABASE_URL` | yes | Existing PostgreSQL/Supabase connection string |
| `SUPABASE_URL` | yes | e.g. `https://<project-ref>.supabase.co` |
| `SUPABASE_ANON_KEY` | yes | Public read-only key. **Never** use `service_role` |
| `CORS_ORIGINS` | no | Comma-separated; defaults to `http://localhost:5173` |
| `PORT`, `NODE_ENV` | no | Defaults `8000`, `development` |

The server now fails fast at start-up if `SUPABASE_URL` or
`SUPABASE_ANON_KEY` is missing, rather than accepting requests it cannot
authenticate.

### `console` (browser, `VITE_*` are baked into the bundle)

| Variable | Required | Notes |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | yes | Same project URL as the server |
| `VITE_SUPABASE_ANON_KEY` | yes | Same anon key; public by design |
| `VITE_GRAPHQL_URL` | no | Defaults to `http://localhost:8001/graphql` |
| `VITE_SITE_URL` | no | Marketing origin for the login page's legal links |

Copy `.env.example` to `.env` and fill in the four Supabase values.

## Google Cloud + Supabase configuration

### 1. Google Cloud project

1. Create a project and enable **Google Cloud → APIs & Services → Credentials**.
2. Create an **OAuth client ID** of type **Web application**.
3. Add the redirect URIs listed below to *Authorised redirect URIs*.
4. Note the **Client ID** and **Client Secret**.

### 2. Supabase project

1. **Authentication → Providers → Google**: enable it and paste the client ID
   and secret.
2. Optionally set **Authentication → URL Configuration → Site URL** to your
   production console origin.
3. Add every console redirect URI under
   **Authentication → URL Configuration → Redirect URLs**.

Google credentials live only in Supabase. They are not added to this
repository and are not required by any Zonatic process.

## Redirect URLs

Supabase sends the browser to Google, then returns to Supabase, then back to
the console. Only the final console URL needs to be allowlisted, but list all
of these:

**Local development**

```
http://localhost:5173/dashboard
```

**Docker Compose (console on port 80 via Caddy)**

```
http://localhost/dashboard
```

**Production**

```
https://<console-host>/dashboard
```

`/dashboard` is used for both the initial sign-in and the OAuth callback, so
one URL per environment is enough.

## Applying the migration

The auth flow needs `users`, `tenant_members`, and `tenant_usage`, which do
not exist in the current database. Apply the migration before first use:

```bash
# Linked Supabase project
supabase db push

# Or directly against the target database
psql "$DATABASE_URL" -f supabase/migrations/20260101000007_console_auth.sql
```

Never run this against the production `zonatic` database without a backup —
it is a schema change. See `supabase/migrations/README.md` for conventions.

## API keys

Keys are generated by `console-api` and stored as a plain SHA-256 hex digest
in `api_keys.key_hash`, matching `apps/api/dependencies.py::_hash_key`. Because the
hash algorithm is identical, a key created in the console authenticates
against the public API with no format change:

```bash
curl -H "Authorization: Bearer zn_live_..." \
  "https://api.zonatic.id/v1/areas?q=kebayoran"
```

- The raw key is returned **once**, in the `createApiKey` mutation response.
- It is never persisted, never logged, and cannot be retrieved again.
- Revocation sets `api_keys.revoked_at`; the public API rejects revoked keys.

## Security notes

- **Tenant isolation.** `tenantId` is only ever read from the verified
  session, never from client input. Every tenant-scoped resolver calls
  `requireWorkspace(context)` first, and list/revoke queries filter on
  `tenant_id`, so one workspace cannot read or revoke another's keys.
- **Unauthenticated requests** get `user: null, workspace: null` and are
  rejected by `requireWorkspace` — there is no anonymous read path.
- **Revoked keys** cannot authenticate API requests (`apps/api/dependencies.py`
  checks `revoked_at`).
- **CORS** is an explicit origin list with credentials allowed, not `*`.

### Known gap: API request count

`tenant_usage.api_requests_total` exists and is surfaced on the dashboard, but
it is **not yet incremented**. Wiring the counter into the public API's
per-request authentication path was deliberately left out of the auth work, so
the dashboard currently reports a real `0` rather than a fabricated number.
Until that instrumentation lands, treat the dashboard's "API requests" figure
as a placeholder, and do not use it for billing or reporting.

## Console routes

| Route | Purpose |
| --- | --- |
| `/login` | Google sign-in. Public; redirects to `/dashboard` if already signed in |
| `/dashboard` | Workspace, key count, request count |
| `/api-keys` | List, create, revoke keys |
| `/` | Redirects to `/dashboard` |

Unauthenticated visits to any protected route are redirected to `/login`.
